# `lcn.storage_fetch`: how a Storage provider serves package objects

The contract through which the Package Manager reads LGX package objects from a Logos Storage provider
(DECISIONS G91, G136, G395). PACKAGE MANAGER l.854-858 leaves the retrieval API of each Storage binding
implementation-defined and requires it documented (PKG-0474); l.1453-1458 requires no common fetch
interface of Storage providers. This document is the retrieval API's half of that duty; each provider
documents its locator encoding (§5). `lcn` is not a reserved prefix (INTERFACE l.249-262), so the contract
is this implementation's by convention.

The Package Manager reaches storage only through the storage module (owner, 2026-11-20): it never links
a storage library. storage_module implements this contract beside its own, inside its own process, over
the node it runs (N-4).

A provider takes the contract by naming its root in `_implements` (INTERFACE l.162-179); the root is
the document's identity (l.141-155), and the SDK's suite checks the committed root against the one the
commitment code computes from the text. A provider and a consumer agree only on that root.

## 2. The document

```cddl
; -- metadata --
_interface = "lcn.storage_fetch"

; How a Logos Storage provider serves package objects to the Package Manager
; (DECISIONS G91, G136, G395; PACKAGE MANAGER l.854-858, l.1453-1458).
; sdk/docs/STORAGE-FETCH.md documents it.

; An LGX source's `object` or `provenance_object`, as the catalog gives it.
; Opaque to the Package Manager; each provider documents its encoding.
lcn.storage_fetch.locator = bstr .size (1..4096)

lcn.storage_fetch.readiness = "starting" / "ready" / "offline"

lcn.storage_fetch.failure = {
  code: "invalid-length" / "invalid-locator" / "not-ready" / "unavailable" / "out-of-range",
  ? detail: tstr .size (1..256),
}

lcn.storage_fetch.stat_object_request = {
  object: lcn.storage_fetch.locator,
}

lcn.storage_fetch.stat_object_response =
  { size: uint64 } /
  { failure: lcn.storage_fetch.failure }

; `length` is 1..1048576 by rule (STORAGE-FETCH.md); a schema cannot bound
; an integer outside the prelude aliases (INTERFACE l.446-458).
lcn.storage_fetch.read_object_request = {
  object: lcn.storage_fetch.locator,
  offset: uint64,
  length: uint32,
}

lcn.storage_fetch.read_object_response =
  { data: bstr .size (0..1048576) } /
  { failure: lcn.storage_fetch.failure }

lcn.storage_fetch.fetch_readiness_request = {}

lcn.storage_fetch.fetch_readiness_response = {
  readiness: lcn.storage_fetch.readiness,
}

lcn.storage_fetch.fetch_readiness_changed_event = {
  readiness: lcn.storage_fetch.readiness,
}
```

The arms of each response are told apart by their single key. The bare method names `stat_object`,
`read_object` and `fetch_readiness` are chosen so that a provider's own primary contract (storage_module's
has `fetch`, `exists` and its download methods) cannot collide with them (INTERFACE l.318-324). The
contract declares no `_sensitive`: package objects are public.

## 3. Calls

- **One object, fixed bytes.** For one provider, a locator always names the same bytes and the same size.
  A provider that cannot keep that answers `unavailable`, and should keep an object it has begun to serve.
  The Package Manager treats every byte as untrusted and verifies the archive in full (PACKAGE MANAGER
  l.397, l.443-444), so a provider that breaks the rule causes a refusal, never an acceptance.
- **`stat_object`** answers the object's size in bytes. The Package Manager refuses an object larger than
  its own archive bound before reading it.
- **`read_object`** answers exactly `min(length, size - offset)` bytes from `offset`; `offset = size`
  answers empty `data`. There is no short read except at the end.
- **The length rule.** `length` is 1 to 1,048,576 (1 MiB). A response then stays far below the 16 MiB
  frame body limit (TRANSPORT l.372), and a consumer's buffer is bounded. The schema cannot say so
  (INTERFACE l.446-458): `length` is `uint32`, and a provider answers `invalid-length` for 0 or more.
- **The order of a provider's checks:** the length, then the locator, then availability (readiness and
  the object), then the range. A bad length is refused whatever the object is.
- **Failures** are the expected outcomes only, each a response arm, never `NOT_READY` or `MODULE_ERROR`
  (RUNTIME l.609-626):
  - `invalid-length`: `length` is 0 or above 1,048,576;
  - `invalid-locator`: the provider cannot interpret the locator; permanent for that provider;
  - `not-ready`: readiness is not `ready` and the provider does not hold the object locally;
  - `unavailable`: the object could not be obtained now (not found, network failure, overload); a later
    call may succeed. A consumer that gets it in the middle of an object resumes from the same offset,
    since the bytes are fixed;
  - `out-of-range`: `offset > size`.

  A provider fault is still an invocation error, and a consumer treats it as a failed retrieval. `detail`
  is text the provider wrote: the consumer never parses it, and logs it only as foreign text, quoted, cut
  and attributed (BCP l.557-558; `logos_sdk/base/logtext`).
- **Long calls.** A read that waits on the network is one Request and its delayed final Response
  (TRANSPORT l.826-828); the caller chooses its own deadline. There is no job identifier and no session:
  reads hold no state for a consumer and survive a lost route, the consumer continuing from its offset
  on the renewed route. Concurrent reads use one route handle each, or prepared calls submitted in turn
  (INTERFACE l.1935).
- **No paths, no transport choice.** The contract returns bytes, never a host path (DECISIONS G99; RUNTIME
  l.3776-3783). Whether a provider retrieves privately or advertises is its own configuration, not a
  request field; storage_module serves the Package Manager's reads with advertising off.

## 4. Readiness

Readiness is the provider's network phase (G136): `starting` until it can retrieve from the network,
`ready` while it can, `offline` after it lost or failed that phase; it may return to `ready`. It is not
Runtime readiness: the instance is Runtime-ready once its listening phase has initialized (RUNTIME
l.601-626). G136's `dht_ready` is the state `ready`.

A consumer subscribes to `fetch_readiness_changed_event`, then calls `fetch_readiness`, then waits for
`ready` if it must (TRANSPORT l.830). A provider publishes the event on every change and on no other
occasion; the initial state is what `fetch_readiness` answers. A provider that is not `ready` MAY serve
an object it already holds locally, so a restart does not block installs from cached objects.

## 5. Locators

A locator is an LGX source's `object` or `provenance_object` (PACKAGE MANAGER l.789-801), opaque to the
Package Manager; each provider documents what it means:

| Provider | Encoding |
|---|---|
| storage_module | the binary manifest CID (G5); documented with Tier 5 steps 5-3b and N-4 |
| `fetch_fake_module` (tests only) | `fetch-fake/<size>/<seed>` (§6) |

## 6. The reference fake provider

`fetch_fake_module` implements the contract for tests; no package of the flake builds it, and N-4
replaces it with storage_module. It has no configuration. A locator `fetch-fake/<size>/<seed>` (size in
decimal, no leading zero) names `size` bytes of BLAKE3's extendable output over `seed`, so a test names
any object without sending its bytes anywhere; a seed beginning `absent-` names an object it cannot
obtain (`unavailable`); any other locator is `invalid-locator`. It starts `starting`, holding nothing.

Its own contract drives it, in every placement: `fetch_fake.set_readiness` moves it to a state (publishing
the event when the state changes) and sets the locators it serves while not `ready`;
`fetch_fake.set_fault` makes one locator answer `unavailable` to its next N reads and stats, or holds each
of its reads some milliseconds before it answers. Its `_implements` literal is the contract's root, and
acceptance fails if the two drift apart.

## 7. The conformance harness

`logos_sdk/testing/storagefetch` checks a provider over route handles the caller materialized, so it runs
wherever a consumer can reach one: the SDK's in-process route, a test Runtime with the provider direct or
hosted (`tests/test_storage_fetch.nim`), and storage_module in N-4. It takes at least four handles, an
optional readiness driver, and a fixture naming at least two objects (locator, size, BLAKE3 digest) and a
locator the provider cannot obtain.

- **The call checks** run everywhere: each object's size; the whole object read in 1 MiB steps and
  compared by digest; empty data at the end and `out-of-range` past it; `invalid-length` for 0 and
  1 MiB + 1, also for the absent locator (the length comes first); `unavailable` for the absent locator;
  four reads of one object at once on four handles agree.
- **The readiness checks** need handles that subscribe: subscribe, then query; one event per change and
  none without one; a read of an object the provider does not hold answers `not-ready` while not `ready`.
  With a driver they move the provider through `starting` (holding the first object), `ready`, `offline`
  and back to `ready`; without one they observe the provider and wait for `ready`.

Serving a held object while not `ready` and refusing a locator are permitted, not required, and are not
checked.

## 8. Grants and placement

A deployment grants, beside the consumer's route to the contract (G140), the authorities event delivery
needs (CA l.244-247): the consumer's `subscribe-event` for `lcn.storage_fetch.fetch_readiness_changed_event`
on that route, and the provider's `publish-event` for it.

Payloads go directly between the two modules' processes (C1). The Package Manager's route to its Storage
provider is an ordinary consumer route (TRANSPORT l.1056-1057): logosd issues it and decides its Hello,
and read responses go from the provider's Module Host to the Package Manager's over their own connection;
the Runtime's carrier holds names and roots, never objects. `tests/test_storage_fetch.nim` checks this
with a hosted consumer reading 4 MiB from a hosted provider. Both ends therefore stay `hosted_dynamic`: a
`direct_*` storage_module or Package Manager would put archives into logosd's process.
